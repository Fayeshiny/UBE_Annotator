# 帧跳转与缓存

## 工作方式

暂停标注时，工作台先通过经过权限检查的帧图片接口显示目标帧，连续播放仍使用原播放视频。
图片与视频是独立资源：图片加载完成并不表示该位置的视频片段已经准备好。
点击播放时保留已显示的目标图片，仅在角落提示准备播放；视频定位、解码并呈现首帧后再交接，避免再次空白。
图片是否显示与是否允许编辑分别控制，准备播放期间不允许提交当前帧标注或分割。

图片就绪且在当前帧停留约 700 ms 后，后台提前定位隐藏的视频；连续跳转会重置等待时间，
不会为每个中间目标启动定位。正在进行或已经完成的同目标准备可以被播放复用，不重复 seek。
准备播放期间暂停邻帧图片预取，把网络优先留给视频。切换目标或任务时取消旧准备的等待和回调。
这会增加停留帧的后台视频流量；原生浏览器缓冲量由浏览器决定。刚跳转就立即点击播放，或网络较慢时，
仍可能等待视频缓冲，但已加载的目标图片会保留。后台准备不会自动播放，失败时可通过点击播放重新尝试。

从播放切换到暂停时，先保留视频已经显示的画面，后台加载同一帧的标注图片，准备好后再交接。
这段时间仅在角落提示“正在准备标注”，不会用全屏加载层遮住画面；图片加载失败也保留暂停画面并提供重试。
暂停后用已停止的播放时间确定帧号；播放中的呈现时间按最近毫秒时间戳匹配，避免时间戳舍入造成帧号偏移。
区间回看由呈现回调触发自动暂停时，使用该回调的帧号，避免高倍速下播放时钟与画面存在差值。
跳到另一帧或重新播放时立即清除旧暂停预览，防止旧画面被当作新目标。

加载中的目标帧与已经显示的帧分别记录。只有目标图片完成解码并与当前帧匹配后，才允许提交当前帧的标注或分割操作。
连续快速跳转时丢弃旧请求的结果，切换任务或退出登录时释放缓存。

图片保持视频原始宽高，使用高质量 JPEG，不改变标注坐标。图片和 SAM 抽帧共用时间戳定位逻辑，
采用 CSV 的 `pts_sec`，避免只用四舍五入后的毫秒时间戳定位时偏移一帧。
JPEG 是有损显示缓存；原视频、已有标注、正式分割掩膜及导出坐标不被转换或修改。

## 缓存与预生成

- 浏览器按标注设备的 `navigator.deviceMemory` 提示选择帧缓存预算，容量和条数先到者为准。
  该提示只反映粗略设备内存，不表示当前可用内存；服务器内存不用于决定浏览器预算。

  | 浏览器报告的设备内存 | 解码画面预算／最多条数 | 压缩 JPEG 预算／最多条数 | 预取候选上限 |
  | --- | --- | --- | --- |
  | ≥8 GiB | 256 MiB／128 | 256 MiB／4096 | 12 |
  | ≤4 GiB | 96 MiB／32 | 64 MiB／1024 | 6 |
  | 未提供、无效或介于两档 | 128 MiB／64 | 128 MiB／2048 | 6 |

  每帧解码估算包含 RGBA 像素及解码 URL 持有的 JPEG。正在显示的单帧若超过预算仍保留，避免无法打开大图。
  两层上限不是整个浏览器进程的内存上限；视频、界面和掩膜另有占用，缓存按使用逐步填充。
- 独立的压缩图片层保留原始 JPEG Blob，按最近访问淘汰。
  从解码层淘汰时仅释放图片与 URL；若压缩层仍有该帧，回看时在本地重新解码，不再请求服务器。
  两层均仅存于当前页面内存，按账号、任务、病例和媒体版本隔离，切换任务、退出或刷新时释放。
  压缩层沿用现有预取逐步填充，不会一次下载整段视频或全部采样点。
- 当前帧加载完成后，最多预取六或十二个候选帧，通常为前后各两帧和前后采样点。
  采样页优先预取采样点，逐帧操作优先预取相邻帧；使用 ↑／↓ 后，非采样页优先预测相对当前帧的 ±5 秒目标。
  大容量档保持原有前六项优先级，额外准备后续采样／相对跳转目标及附近帧。
  实际数量进一步按当前图片字节和解码条数预算缩小，为当前画面和图片大小差异预留空间；
  超大图片可能不预取。已缓存的优先候选计入计划并刷新最近访问顺序，避免被较远预取淘汰。
  后台始终仅一个图片请求，不会随缓存扩容增加并发。
  当前请求优先，过期预取取消。跳到正在预取的同一帧时，复用原来的下载和解码，不取消重下。
  已发出的请求无法改变浏览器优先级；如果它被服务器以 429／503 拒绝，选中后最多以前台方式重试一次。
- 服务器帧缓存位于 `SSI_DATA_DIR/cache/frames/`，默认 2 GiB。
  按视频及时间戳表的版本区分，源文件变化后不会复用旧版图片。
- 按需抽帧一次最多生成五个相邻帧；固定采样点预生成只生成该采样帧，避免对整段长视频逐帧存图。
- 全局最多同时运行两个图片解码任务，后台最多使用一个名额；前台等待有数量与时间上限。
  后台预生成不会无限创建任务，忙时让出资源。

首次打开未缓存的位置仍需要服务器抽帧和网络传输，不保证比所有情况下的视频定位更快。
主要收益来自相邻帧预取、采样点预生成以及重复访问已解码的图片。
这里扩大的是平台管理的帧图片缓存；连续播放的原生视频缓冲仍由浏览器管理，不保证保存整段视频。

## 运行配置

在 `deploy/production.env` 中按需设置，修改后重启后端：

```bash
# 帧图片缓存的磁盘上限，单位 MiB（默认 2048）。不包含原视频和 SAM 缓存。
SSI_FRAME_CACHE_MAX_MB=2048
# 是否在视频导入成功后自动安排采样点预生成，0 关闭，默认 1。
SSI_FRAME_CACHE_PREWARM=1
```

帧图片属于可重新生成的缓存，备份脚本继续排除 `cache/`。
不要删除 `cases/` 下的视频、时间戳表或分割文件来清理缓存。

新导入视频会自动安排采样帧预生成，已有病例在工作台打开时也会安排预生成。
如需在正式开始标注前离线准备指定病例，可在停止服务后执行：

```bash
set -a
source deploy/production.env
set +a
backend/.venv/bin/ssi-annotator warm-frame-cache CASE_ID --interval-ms 5000
```

该命令与正式服务共用数据目录锁；正式服务运行时会拒绝离线预热。
在线预热应通过工作台触发，以共用同一个进程的磁盘缓存索引和解码并发预算。

## 测量口径

需要区分三种路径：

1. **服务器未命中**：包括首次启动 FFmpeg 抽帧、JPEG 生成、传输和浏览器解码。
2. **服务器命中**：已有 JPEG，仍包括权限检查、网络传输和浏览器解码。
3. **浏览器命中**：当前页面保留了已解码图片，通常不需要新的图片请求。

帧接口的 `X-Frame-Cache` 响应头用于区分服务器 HIT/MISS。
浏览器 User Timing 中的 `ssi-frame-ready` 记录请求到图片准备就绪的时间，包含是否使用页面缓存；
它不包含显示器刷新延迟，不能与以画面绘制完成为终点的基准混用。

基准使用服务器本机 Chrome 与隔离的测试数据库，在本地及模拟带宽/延迟条件下进行。
这些数值用于比较代码路径，不代表公网 Funnel 或标注者设备的真实延迟。

## 本机对照结果（2026-10-20）

使用约 2.51 GB、1080p、约 60 fps 的播放文件，Chrome 151，无 CPU 限速。
模拟下载带宽 20 Mbps、网络延迟 80 ms，关闭浏览器 HTTP 缓存以区分服务器缓存与已解码复用，
操作系统文件缓存未清空。每组随机跳到 4 个不同位置，样本很小，P95 在这里实际等于最大值。

| 路径 | 中位耗时 | P95 / 本组最大值 | 4 次跳转观测传输量 |
| --- | ---: | ---: | ---: |
| 原视频首次随机定位 | 404 ms | 447 ms | 约 2.61 MB |
| 原视频重复定位 | 96 ms | 116 ms | 约 0.32 MB |
| 帧图片首次生成（MISS） | 378 ms | 566 ms | 约 0.47 MB |
| 帧图片服务器缓存命中（HIT） | 170 ms | 179 ms | 约 0.47 MB |
| 测量脚本复用已解码图片 | 29 ms | 29 ms | 0 |

这组随机跳转中，图片传输量约减少 82%；视频可能预读后续片段，传输量属于测量窗口近似值。
**首次抽帧并非稳定加速**：其中一个目标图片首次生成为 566 ms，而视频定位为 447 ms。
另两组实验中，尚未完成浏览器预取的相邻图片请求也比已缓冲视频慢。因此预生成、预取及页面缓存是优化的核心。

上述属于媒体通路测量，不是完整点击交互测试；“已解码复用”使用测量脚本自身缓存。
实际工作台的缓存上限、快速跳转、播放交接与帧号正确性另外通过浏览器交互测试验证。
原始数据位于 [benchmarks/](benchmarks/)，可复现脚本为 [benchmark-seek.mjs](../scripts/benchmark-seek.mjs)。
脚本需要 Playwright Core 和本机 Chrome；测试工具单独安装，不属于运行平台的依赖。

同一模拟网络下，实际工作台每次操作前留出 1.2 秒给预取：

- 连续查看相邻帧，5 次全部命中浏览器缓存，中位数约 28 ms。
- 在采样页按 L 查看下一采样点，5 次全部命中浏览器缓存，中位数约 29 ms。
- 从非采样点开始连续按 ↓ 跳 5 秒，第一次仍需请求；随后 3 次预取命中为 28.4、29.7、30.5 ms。
- 四个相距很远的位置反复查看时，96 MiB 缓存不足以同时保留全部位置及邻帧，重复访问仍可能走服务器缓存。
  1080p 图像按 RGBA 估算每张约 8 MiB，实际可保留约 11 张，并非总能达到 32 张。

浏览器回归测试使用带编号与灰度编码的合成视频，验证加载期间编辑禁用、乱序响应像素与帧号匹配、

本轮 113 项后端、36 项前端测试通过，前端生产构建通过。

随后修复暂停画面被加载层遮住的问题，45 项前端测试与构建通过。Chrome 合成视频回归覆盖 1.5 秒图片延迟、
加载失败重试、暂停后跳帧、暂停后继续播放、4 倍速区间自动暂停及视频结束，六项均通过，无页面 JS 错误。
使用视频顺序解码的参考图像核对冻结画面帧号；等待精确图片期间保持标注禁用。
结果见 [暂停交接测试记录](benchmarks/ui-pause-20261020.json)。

## 优化调查与后续方案（2026-10-20）

当前开发病例 S_A 使用 `S_A_recovered.mp4`，共 117827 帧、1963.95 秒、约 2.51 GB，
视频码率约 10.24 Mbps。文件已将 moov 放在开头，关键帧通常每 35 帧一个（约 0.58 秒）。
现有 `S_A_web.mp4` 只有 6200 帧、103.42 秒，不能替代完整病例。

以下第 1、2 项已随后实现，第 3、4 项仍为后续方案：

1. 保留正在预取的同目标请求，导航时将其提升为当前请求。原 hook cleanup 和缓存 load 会先取消它，
   造成已传输部分被丢弃；现在复用下载，繁忙时单次前台重试，旧目标仍会取消。
2. 在已解码工作集外增加有界 JPEG Blob 缓存。96 MiB 解码预算只能容纳约 11 张 1080p 图片；
   已预热的 393 个采样 JPEG 合计约 43.5 MiB，新增的 64 MiB 压缩层可以保留更多已访问的回看位置，
   回看仅在本地重新解码。继续按任务、账号与媒体版本隔离，退出时释放。
3. 让后台视频定位与邻帧图片预取共享网络优先级。目前点击播放会暂停图片预取，
   700 ms 后的后台定位仍可能与图片预取竞争。可针对明确点击／采样点操作更早准备，
   快速跳转保留防抖；等待值需要实测。
4. 增加可选择的低码率播放副本，暂停标注保持原尺寸精确图片。
   不降低帧率，生成后逐帧验证时间对应关系，避免改变已有帧号与标注位置。

对 1137–1147 秒同一段做临时编码实验，所有输出均为 600 帧／10 秒，
H.264、veryfast、2 线程、GOP 15：

| 版本 | 10 秒大小 | 近似码率 | 相比源视频包 |
| --- | ---: | ---: | ---: |
| 源视频压缩包 | 12.78 MB | 10.22 Mbps | — |
| 1080p CRF23 | 9.84 MB | 7.87 Mbps | 减少 23.0% |
| 720p CRF23 | 4.02 MB | 3.22 Mbps | 减少 68.5% |
| 1080p CRF20 | 14.44 MB | 11.55 Mbps | 增加 13.0% |

输出大小包含容器开销，源窗口统计为压缩视频包字节。该实验只比较一个片段的体积和编码结果，
没有评估医学画面细节或实际浏览器跳转延迟，不能将体积减少直接解释为等比例提速。
720p 会损失播放细节；需要保留原画选项，并验证其能否满足播放查看需求。
更密集关键帧也可能增大码率，不能单靠缩短 GOP 保证更快。
本次临时视频均已删除，活动媒体和数据库未修改。
原始统计见 [播放副本片段测量](benchmarks/proxy-sample-20261020.json)。

## 预取复用与两级缓存验证（2026-10-20）

77 项前端测试与生产构建通过。真实 Chrome 使用隔离合成数据完成五项工作台检查与四项浏览器缓存检查：

- 持续下载中的目标预取被选中后只有一次 HTTP 请求，未被中止；加载期间仍禁止标注。
- 被选中的预取遇到 429 后，只有一次前台重试，最终显示帧与请求帧一致。
- 查看 21 张真实尺寸 1080p JPEG，使第一张从 96 MiB 解码层淘汰；回看时该帧总 HTTP 次数仍为一次，
  重新解码后的全部像素哈希与最初相同。
- 离开工作区和退出会取消请求、释放 URL；重新进入不能复用旧任务的压缩缓存。
- 连续快速跳转取消被升级但已过期的请求；迟到结果不能覆盖最新目标帧。
- 浏览器实测压缩层 LRU 字节统计、清空、超预算图片不保留，以及清空后迟到响应不重新入缓存。

全部九项检查通过，无页面 JS 错误。记录见 [工作台缓存回归](benchmarks/ui-cache-regression-20261020.json)
与 [浏览器压缩缓存回归](benchmarks/blob-cache-browser-20261020.json)。
这些检查证明减少了请求和保留了像素一致性，不代表所有公网冷跳转都能达到固定延迟。

现有开发病例 `S_A` 的 393 个五秒采样帧已提前生成，用时约 81 秒、占用约 43.5 MiB。
此操作仅新增可再生成缓存，未迁移或修改开发库标注，也未把该病例加入正式数据库。

## 扩容验证（2026-10-20）

82 项前端测试、生产构建及八项隔离 Chrome 工作台检查通过，无页面 JS 错误。
测试显式控制浏览器内存提示，帧接口使用合成的真实尺寸 1080p JPEG；容量检查中关闭额外预取下载，
以区分解码缓存容量与后台填充。结果如下：

- ≥8 GiB 档连续查看 21 张画面，早先解码 URL 仍保留，回看复用同一 URL。
- 继续查看到 40 张后，较早的非预测目标画面从解码层淘汰，回看只需本地重新解码；新增 HTTP 请求为零，全部像素哈希一致。
- 内存信息未知档在 14 张时保留、20 张时淘汰较早画面；≤4 GiB 档在 10 张时保留、20 张时淘汰。
  两档淘汰后的回看也均无新增 HTTP 请求。
- 同目标预取复用、忙时单次前台重试、快速跳转取消旧结果、退出释放资源均保持通过。

原始记录见 [扩容浏览器回归](benchmarks/ui-large-cache-20261020.json)。
容量收益主要体现在重复查看和可预测跳转，不能将缓存容量增长倍数解释为跳帧延迟等比例下降。
开发与正式服务均已提供新构建，保存标注后强制刷新页面即可使用。


## 完整视频临时缓存（2026-10-20）

进入已就绪的工作台后，以经过权限检查的 HEAD 获取文件大小及媒体版本，再串行下载每段最多 4 MiB 的 Range。
每段验证状态码 206、Content-Range、版本和实际长度，全部写入并校验总长度后才公开 Blob URL。
优先写入浏览器 OPFS 文件，缺少 OPFS 时回退到独立 IndexedDB Blob 分段；不把整段视频读入 JS ArrayBuffer。
下载前检查可用配额，空间不足、认证失败、视频版本变化或下载异常均保留在线工作流程。

下载在播放、准备播放、手动暂停或标签页隐藏时让出网络，恢复时从最后一段已提交的位置继续。
下载完成后在暂停状态下切换资源，使用原始播放文件本地解码显示帧，沿用原时间戳表、原分辨率和原标注坐标。
只有精确定位完成才允许掩膜编辑；快速跳帧取消过期的定位回调。本地帧解码失败可回退到服务器图片。
完整缓存不触发 SAM，不缩放视频，不重编码视频。

清除缓存会撤销 URL、删除当前实例的本地文件或数据库，并返回在线画面。播放中先暂停才可清除。
切换任务、退出工作台及注销会释放当前缓存；此版本为当前工作台的临时缓存，不支持跨刷新复用或跨会话断点续传。
浏览器异常退出时未完成的清理可能由浏览器存储管理回收，可通过浏览器站点数据设置清除残留；不会读取其他任务缓存。
标注保存、SAM 推理、掩膜读取仍需要服务器，完整视频缓存不等于整个标注平台离线运行。

验证使用独立数据库和合成视频，未修改开发或正式标注数据。记录见
[完整视频缓存浏览器回归](benchmarks/whole-video-cache-browser-20261020.json)。


## 缓存未完成时优先显示目标帧（2026-10-20）

跳转处理函数立即暂停完整视频下载并中止当前 Range，目标 JPEG 就绪或失败后空闲 1 秒再恢复后台缓存。
连续拖动反复更新空闲计时，不在每次鼠标移动后重新抢占带宽。初始目标帧也优先于完整缓存下载。
暂停标注时移除远程 video 源并调用 load() 释放其网络请求；取消原来空闲 700 ms 自动定位隐藏视频的逻辑。
仅明确点击播放时才挂载远程视频并定位。实际播放暂停时先保留已解码画面，等精确 JPEG 就绪再移除远程源。
完整缓存后的本地 video 定位不受此限制，不降低 JPEG 质量、分辨率或修改时间戳。

相同 1080p 合成视频、4 Mbps/80 ms 模拟链路、完整缓存未完成时，对两组独立病例进行 6 次冷目标时间轴跳转。
交互开始至目标帧 ready 再经过两次动画帧：旧调度中位 1567.65 ms、最大 1653 ms，新调度中位 737.15 ms、最大 788.30 ms。
这次测试全部低于 1 秒，但不代表所有公网/SSH 链路及设备都能达到该上限。图片实际下载时间受有效带宽约束。
101 项前端测试及生产构建通过；额外 Chrome 验证正在下载的分段被前台抢占、空闲续传、无隐藏媒体流量、明确播放/实际暂停，
以及 OPFS/IndexedDB 完整缓存、像素一致性、媒体离线、本地跳帧/播放/暂停、清理、重试、任务隔离、配额回退和注销均通过。
原始数据见 [跳帧优先调度对照](benchmarks/navigation-priority-20261020.json)。

## 当前位置优先与附近帧块（2026-10-21）

完整文件下载仍采用每段最多 4 MiB，但不再只从文件开头顺序填充。
新增经过病例权限和媒体版本检查的 `video-index`，服务端从真实 packet 的 PTS、文件位置、大小及关键帧标记生成字节范围。
浏览器优先下载目标帧所在关键帧组、前后约 1 秒位置及下一采样网格点对应的字节块，再补齐未下载的空洞。
跳转时取消旧的未提交请求，已提交块不重复下载；索引不可用则回退到顺序补齐，不按平均码率猜测偏移。
OPFS 按物理偏移写文件，IndexedDB 按偏移存 Blob 并按键排序组合；下载进度是已验证不同块的字节总量。
只有覆盖完整文件且长度校验通过才发布完整视频 URL，局部字节缓存不会伪装成可播放的完整 MP4。

随机跳转时仍优先独立请求目标高清 JPEG，不等待视频索引、完整文件或邻帧块。
目标显示后等待 200 ms，再低优先级读取其所在 5 帧组（排除已显示的目标帧），服务端优先排列下一帧、上一帧，再向两侧扩展。
帧块传输协议为 4 字节大端 JSON 长度、版本及帧号/长度索引，随后为原始 JPEG 字节；不重编码、不降分辨率。
每张完整 JPEG 到达即进入浏览器压缩缓存，不等待整块完成，随后按原有解码缓存预算准备显示。
前台换目标会中止旧帧块下载；已完整接收的同版本 JPEG 可继续复用，迟到或中断后的数据不能覆盖新目标。
附近块准备期间完整视频下载继续让出带宽，结束后空闲 1 秒再恢复。块接口不可用或繁忙则沿用单帧预取。

这一版包含两种不同的局部缓存：附近 JPEG 可立即服务逐帧查看；优先下载的视频字节在完整覆盖后才用于完整本地视频播放。
没有加入缩略图预览，也未实现跨刷新持久化。


验证：114 项前端测试、127 项后端测试及生产构建通过。隔离 Chrome 分别验证 OPFS/IndexedDB：
跳到 650 帧后首先请求 `bytes=75497472-79691775`，随后处理附近及下一采样点，再回到 `bytes=0-4194303` 补洞。
两种存储重组后的约 102 MiB 文件，全部 26 个块的 SHA256 均与原文件一致。
目标图在附近块被刻意延迟时已经可用；附近帧回看零新增单帧请求、像素一致；跳到另一位置会取消旧视频区域请求，
迟到的旧帧块不能覆盖当前画面。渐进读取另有单测验证第一张 JPEG 在帧块尾部尚未到达时即可使用。
4 Mbps/80 ms 下 6 次冷目标随机跳转中位 736.75 ms、最大 786.30 ms；此数据仅代表该合成测试，不保证用户 SSH 链路上限。

## 未完成缓存时的连续播放

子任务切分减少一次需要缓存的视频总量，未必降低每秒播放所需带宽。当前 SSI_0039 首段约 579 MB/310 秒，平均约 14.95 Mbps。8 Mbps/80 ms 模拟链路会反复等待网络，不能保证按 1× 实时连续播放；可暂停等待“本段视频已缓存”后使用本地文件。

播放器现在显示缓冲状态，按浏览器 MediaError 区分传输中断、解码失败与源格式错误；失败后保留最后显示帧，点击“从当前帧重试播放”重新加载并继续，完整浏览器缓存与标注无需刷新。控制台 `ssi-video-error` 包含错误代码和浏览器详情。此改动改善提示与故障恢复，不提升实际链路吞吐量，也未确认用户那次原始加载失败的具体原因。验证见 benchmarks/playback-recovery-20261021.json。


## 在线播放分块及 HTTP 协议诊断

原生播放器现在使用独立的 `video?...&playback=true` 地址，开放式 Range 响应上限为 2 MiB，浏览器自动请求后续片段，避免单次转发响应持续承载几百 MB。整段缓存继续使用原始地址、精确的 4 MiB Range 和原校验规则，避免改变完整文件重组。编码、分辨率、帧号及文件字节不变。

媒体出错暂停后，即使当前 JPEG 或邻帧预取挂起，也会让完整缓存自动续传；缓存暂停提示区分播放、前台帧、隐藏页面、手动暂停和索引准备。MediaError 4 可能是请求加载失败，也可能是格式不支持，不据此直接认定文件损坏。

Uvicorn `Invalid HTTP request received` 的警告会附加 `protocol=...`，分别识别 TLS、HTTP/2、SSH、SOCKS5、普通 HTTP 解析失败和未知协议。受限诊断记录位于 `cache/http-protocol-errors.jsonl`（128 KiB，保留一个滚动文件），仅记录分类、时间、异常类、数据长度及首字节数值，保留凭据和媒体数据的隐私。206 Partial Content 是正常 Range 响应。

验证：本机原首段连续播放超过 18 秒，无媒体错误，30 个媒体响应均不超过 2 MiB；8 Mbps 模拟链路仍会等待网络，但没有媒体错误。隔离测试故意挂起当前 JPEG/邻帧请求，发生原生媒体错误后完整缓存仍自动续传。见 benchmarks/bounded-playback-20261021.json。上述验证不能替代标注者实际 SSH 链路复测。
